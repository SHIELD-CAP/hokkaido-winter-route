# state

两个定时任务（晚间日报 20:20、晨间复查 06:20）每次运行结束前，把这次的结论写进这里；下一次运行读上一次的结论，写“和昨晚比”哪里变了。判级只看当次取到的数据，不因为上一次报过就沿用。2026-11-26 下午启用；当晚 20:20 那次没写进来（原因见下面“写入测试”），重建任务后从 11-27 06:20 起写入。

## 文件

- `evening.json`：最近一次晚间日报的结论，每次覆盖。
- `morning.json`：最近一次晨间复查的结论，每次覆盖。
- `log/年/月/日-evening.json`、`日-morning.json`：每次结论的存档（日期是东京时间的运行日期），内容和上面相同。

谁读：晚间日报读 `evening.json`（30 小时以内的才用），写“和昨晚比”；晨间复查也读 `evening.json`（16 小时以内的才用），写“和昨晚的日报比”。`morning.json` 和 `log/` 目前只存档，没有任务读，留作以后回测。

## 格式

下面是格式示例，不是真实结论：

```json
{"run": "evening", "run_time": "2026-11-26T20:31+09:00", "rules": "v6（2026-11-26 修订）",
 "msm": "仓库副本，11-26 19:40 取，MSM 11-26 15:00 起算",
 "days": [
  {"date": "2026-11-27",
   "a": {"去程高速": ["🟠", "结冰", "O3", "09–10"], "旭川—美瑛—白金": ["🟢"], "回程山路": ["🟢"], "回程高速": ["🟢"]},
   "b": {"06–09": ["🟠", "结冰", "O3", "道央道北広島—千歳"], "09–12": ["🟢"], "12–15": ["🟢"], "15–18": ["🟢"], "18–21": ["🟢"], "21–24": ["🟢"]}}
 ],
 "closures": "未查到封闭消息",
 "missing": ["B4 集合预报"]}
```

- `run`：evening（晚间日报，days 是明天起的七天）或 morning（晨间复查，days 是今天和明天；已经过去的时段写 `["已过"]`）。
- `a` 是路线甲（一日游）的四段：去程高速、旭川—美瑛—白金、回程山路、回程高速；`b` 是路线乙（机场线）的六个时段。
- 每一项是 `[等级, 类型, 规则编号, 时段或路段]`。等级用 ⬛🔴🟠🟢⬜ 五个符号；🟢 只写 `["🟢"]`，⬜ 写 `["⬜", "缺什么"]`。规则编号写触发等级的那一条，对应 `rules/v6.md`（例如 R8 是雪带，O3 是结冰）。
- `msm` 是这次用的 MSM 来源和起算时刻；`closures` 是运行时查到的封路、停运；`missing` 是没取到的数据。
- 2026-11-28 晚起（提示词 v7，做法 B）多了四项：`engine` 是这次用的程序结果（存档文件、几点算的、代码提交号、离运行时刻几小时）；`a_engine`、`b_engine` 是程序的等级，格式和 `a`、`b` 相同，从 `scripts/engine_summary.py` 写出的 `/tmp/engine_state.json` 照抄；`changes` 列出最终等级和程序不同的每一处（where 哪一段或哪个时段、engine 程序的等级、final 最终等级、why 依据），没有改动写 `[]`。`a`、`b` 仍是最终等级，`rules` 写“v7（做法 B）”。冬天结束后两栏分别打分。
- 提交者名写 Claude，提交信息是“晚间日报结论 日期”或“晨间复查结论 日期”。写入失败时任务不重试，只在报告的“数据情况”里写明错误。
